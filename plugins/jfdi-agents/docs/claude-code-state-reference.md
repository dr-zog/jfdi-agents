# Claude Code agent-team state filesystem reference

> **Version-pinned.** Observed against **Claude Code `2.1.116`** on Windows (Git Bash) in April 2026. The filesystem layout described here is **not a public Claude Code API** — fields, filenames, and semantics can change in future versions. If Claude Code's format drifts, this document is the single place to re-verify against, and the Go state-inspection binary built on top of it (see repo issue tracker) must be re-tested against the new version.
>
> **Purpose.** This reference documents what Claude Code writes under `~/.claude/teams/<team>/` and `~/.claude/tasks/<team>/` during normal agent-team operation. It is the spec the `team-inspect` Go binary parses, so that the TeamLead's state diagnosis becomes deterministic, fast, and free of ad-hoc Bash + Python gluing. Generated by running the six-scenario recon in `docs/recon-runbook.md`.

## Top-level layout of `~/.claude/`

Relevant-to-teams subdirectories (there are others, e.g. `projects/`, `sessions/`, `plugins/`, that are out of scope here):

```
~/.claude/
├── teams/
│   ├── <team-name>/           # one dir per active team (lowercase — see note)
│   └── default/               # system special: see § "The default team"
└── tasks/
    ├── <team-name>/           # one dir per active team (matches teams/ directory name)
    └── <session-uuid>/        # one dir per session for session-local (non-team) tasks
```

Both `teams/` and `tasks/` exist at all times once Claude Code has been used; the `<team-name>` subdirs are created at `TeamCreate` time. Old team directories are retained when the owning Claude Code session ends — they become **zombie teams** (see § "Zombie detection") unless `TeamDelete` was called.

**Team-name casing.** Claude Code accepts the casing the caller passed to `TeamCreate` as the `team_name` in `~/.claude/teams/`, but `~/.claude/tasks/` is always lowercased. Passing a mixed-case name splits the two subsystems. The plugin mitigates this by requiring all-lowercase kebab-case team names from the outset (see `team-lead-playbook.md` § 1.3 and § 1.5). A future version of Claude Code may fix the inconsistency; until then, the mitigation stays.

## Per-team layout

For a team created with no activity — the "fresh team" baseline observed in Scenario 1:

```
~/.claude/teams/<team-name>/
└── config.json                # team metadata + members array (incl. lead)
~/.claude/tasks/<team-name>/
└── .lock                      # 0-byte lockfile (present from TeamCreate)
```

No `inboxes/` directory exists yet. No `.highwatermark` in tasks. These are created lazily — inbox files when the first message is sent to that teammate, `.highwatermark` when the first task lands.

As activity accumulates:

```
~/.claude/teams/<team-name>/
├── config.json                # mutated on member join/leave
└── inboxes/                   # created lazily (first SendMessage to any teammate)
    ├── <teammate-name>.json   # one JSON array per teammate, per team
    ├── team-lead.json         # lead has its own inbox
    └── ...
~/.claude/tasks/<team-name>/
├── .lock
├── .highwatermark             # created when first task/event lands; small integer
└── ...                        # per-task files TBD in Scenario 3
```

## `config.json` schema

Observed keys and value shapes:

| Key | Type | Notes |
|---|---|---|
| `name` | string | The name passed to `TeamCreate`. Case-preserved in this file. |
| `description` | string | Human-readable team purpose. |
| `createdAt` | integer | Unix epoch **milliseconds**. |
| `leadAgentId` | string | `"<lead-name>@<team-name>"`. `<lead-name>` is the literal string `team-lead`. |
| `leadSessionId` | string (UUID) | The Claude Code session UUID for the lead. Transcript at `~/.claude/projects/<project-hash>/<leadSessionId>.jsonl` (exact path TBD — `projects/` layout not yet recon'd). |
| `members` | array of Member | Includes the lead as its first member. Ordered by join time. |

### The Member object

The lead member and spawned-teammate members share a common schema but the lead has fewer fields:

**Lead member (minimum shape):**
```json
{
  "agentId": "team-lead@<team-name>",
  "name": "team-lead",
  "agentType": "team-lead",
  "model": "claude-opus-4-7[1m]",
  "joinedAt": 1776765635634,
  "tmuxPaneId": "",
  "cwd": "C:\\Users\\andre\\AICode\\atdd-agents",
  "subscriptions": []
}
```

**Spawned teammate member (adds fields):**
```json
{
  "agentId": "<name>@<team-name>",
  "name": "<name>",
  "agentType": "<subagent-type>",
  "model": "<model-string>",
  "joinedAt": <epoch-ms>,
  "tmuxPaneId": "in-process" | "<tmux-id>" | "",
  "cwd": "<abs-path>",
  "subscriptions": [],

  "color": "blue" | "green" | ...,
  "prompt": "<full spawn-time prompt text>",
  "planModeRequired": false | true,
  "backendType": "in-process" | ...
}
```

Per-field notes:

- **`agentId`** — the canonical addressable identifier. Used as the `to:` argument for `SendMessage`. For the lead the `name` is always `team-lead` (never the role name).
- **`name`** — the short addressable name within the team. Unique within the team.
- **`agentType`** — for the lead, `team-lead` (literal). For spawned teammates, the `subagent_type` passed to the `Agent` tool (e.g. `recon-cooperative`, `architect`, `general-purpose`). Note `general-purpose` is a built-in backstop agent type.
- **`model`** — the model string. Free-form; Claude Code accepts both short forms (`sonnet`, `opus`) and fully-qualified (`claude-opus-4-7`, `claude-sonnet-4-6`). Contains `[1m]` suffix when the 1M-context Opus variant is selected. The string is recorded verbatim, not normalised.
- **`joinedAt`** — epoch millis. For the lead this equals `createdAt`; for spawned teammates it's the spawn-tool-call time.
- **`tmuxPaneId`** — an identifier for where the teammate's interactive session lives. `""` for the lead (runs in the user's foreground terminal). `"in-process"` for spawned teammates running as in-process subagents. Real tmux pane IDs appear when tmux integration is enabled.
- **`cwd`** — working directory for the teammate's commands. Inherits from the spawning session (normally the user's project root).
- **`subscriptions`** — an array. Always empty in observed cases. Purpose TBD — possibly a future channel-subscription mechanism. The Go tool should surface this field but not assume anything about its contents.
- **`color`** *(non-lead only)* — UI visual cue.
- **`prompt`** *(non-lead only)* — **the full spawn-time prompt given to the teammate**. Multi-line, often quite long. This is the reconstruction-quality record of "what was this agent told to do when it was spawned." Very useful for post-hoc forensic diagnosis.
- **`planModeRequired`** *(non-lead only)* — whether the teammate is constrained to plan mode.
- **`backendType`** *(non-lead only)* — `"in-process"` observed. Likely other values exist for different execution backends.

## Inbox schema (from `default` team and `sptest-c-1015` observations)

Observed at `~/.claude/teams/<team>/inboxes/<teammate-name>.json`:

```json
[
  {
    "from": "team-lead",
    "text": "Andy would like to know: how long might a moderate concussion last? ...",
    "summary": "Concussion duration question from Andy",
    "timestamp": "2026-04-16T21:18:15.553Z",
    "read": false
  }
]
```

**Key observations:**

- **Each inbox is an array of messages** — probably appended when new messages arrive, never deleted (read messages stay in the array with `read: true`). To be confirmed in Scenario 4.
- **Per-message schema**: `from`, `text`, `summary`, `timestamp`, `read`. All observed messages have all five fields.
- **`read` is the read/unread flag** — a simple boolean. This is the authoritative signal for the Go tool's "unread count" computation. **No file move, no separate index, no tombstone** — it's just a flag on the message record.
- **`timestamp` is ISO-8601 string** — note the format inconsistency with `config.json`'s `createdAt` which is epoch millis. The Go tool will need to handle both.
- **`summary` is a short descriptor** distinct from the full `text` — presumably for quick scan-ability in UI. Teams that use `summary` consistently get better lead-level scanning; teams that don't pass a summary presumably get an empty string or missing field (TBD).

**Inbox lifecycle (inferred, to be validated):**

- An inbox JSON file is created the first time another teammate sends a message to this recipient.
- The file grows as messages accumulate (array append).
- When the recipient reads a message, the corresponding element's `read` flag flips from `false` to `true`. The message stays in the array.

## The `default` team

There is always a `~/.claude/teams/default/` directory present. Its shape differs: it has **only** an `inboxes/` subdirectory, no `config.json`. It appears to be a shared system-level inbox used by Claude Code sessions not currently inside an explicit team (or for cross-team messages before a team exists). The `dr-susan.json`, `Orchestrator.json`, `Sentinel.json`, `worker-1.json` files in it are leftovers from past non-team sessions.

The Go state-inspection tool should **ignore the `default` team** — it's not a real team and has no `config.json` for the tool to parse.

## `tasks/<team>/` initial state

For a fresh team with no task activity:

- `.lock` — 0-byte lockfile. Present at TeamCreate time.
- No `.highwatermark`, no other files.

For a team with past task activity (observed on `sptest-c-1015`) or a UUID-scoped session-local task pool:

- `.lock` — 0 bytes.
- `.highwatermark` — a very small file (2 bytes in one observation) containing a plain integer (`12` observed). Likely a monotonic counter of events or tasks. TBD whether tasks themselves live in per-task JSON files, in a single events.json, or in some other form — to be characterised in Scenario 3.

## Scenario-by-scenario recon log

### Scenario 1 — Fresh team (baseline) — COMPLETE

Observed 2026-04-21 against Claude Code 2.1.116.

Team `recon-s1-fresh` created by a human-driven Claude Code session. Immediately after `TeamCreate`:

- `~/.claude/teams/recon-s1-fresh/config.json` exists (573 bytes), with the single-member structure documented above. Lead is `team-lead@recon-s1-fresh`, model `claude-opus-4-7[1m]`, `tmuxPaneId: ""`.
- `~/.claude/tasks/recon-s1-fresh/` exists with only `.lock` (0 bytes). No `.highwatermark`.
- No `inboxes/` subdirectory anywhere for this team.

**Confirmed findings from Scenario 1:**

- TeamCreate creates both `teams/<name>/` and `tasks/<name>/` eagerly.
- `inboxes/` is NOT created at TeamCreate time — it's lazy on first message delivery.
- `.highwatermark` is NOT created at TeamCreate time — it's lazy on first task activity.
- The lead is registered as a first-class `members[]` entry at TeamCreate time.
- Team-name casing is preserved in `config.json` and in `~/.claude/teams/<name>/`; `~/.claude/tasks/<name>/` follows the caller's casing when lowercase (matches observed behaviour for `recon-s1-fresh`). Mixed-case casing behaviour to be re-tested if the mitigation ever changes.

### Scenario 2 — Two spawns — IN PROGRESS (S2a complete, S2b pending)

**S2a: after spawning `recon-alpha` (recon-cooperative, Haiku model).**

Three filesystem deltas observed:

1. `config.json.members[]` gained a second entry for `recon-alpha` with the full non-lead member schema. Confirms the Scenario-1 schema: `color`, `agentType`, `model`, `prompt` (full spawn text), `planModeRequired`, `backendType`. `tmuxPaneId: "in-process"` as expected.
2. **New file: `inboxes/team-lead.json`** — the LEAD's inbox was created even though the user never called `SendMessage`. It was populated by:
   - recon-alpha's "acknowledged" reply (agent-body-driven, per the `recon-cooperative.md` instructions).
   - recon-alpha's human-prose idle notification (also agent-body-driven).
   - A **harness-injected** structured idle notification (see Finding 3 below).
3. `recon-alpha`'s own inbox file does NOT exist. The spawn prompt was delivered as a conversation turn directly, not via the inbox layer.

**Finding 1: Spawn prompts do not flow through the inbox layer.** The member's initial prompt lives in `config.json.members[i].prompt` and is injected into the teammate's conversation as a system/user turn by the harness at spawn time. The inbox layer is purely for **`SendMessage`-originated** messages. Consequence: a recipient's `inboxes/<name>.json` file is created lazily — first when another teammate first `SendMessage`s them.

**Finding 2: Messages in the inbox carry a `color` field** (inherited from the sender's `config.json` color). Extends the inbox-message schema documented in Scenario 1:

```json
{
  "from": "recon-alpha",
  "text": "...",
  "summary": "...",
  "timestamp": "2026-04-21T11:14:04.743Z",
  "color": "blue",
  "read": true
}
```

`color` was not present in the older `default/inboxes/dr-susan.json` observation — presumably added in a later Claude Code version, or absent when the sender had no assigned color.

**Finding 3: Harness-injected structured idle notifications.** When a teammate goes idle after its turn, Claude Code automatically writes an additional inbox entry to the lead's inbox:

```json
{
  "from": "recon-alpha",
  "text": "{\"type\":\"idle_notification\",\"from\":\"recon-alpha\",\"timestamp\":\"...\",\"idleReason\":\"available\"}",
  "timestamp": "2026-04-21T11:14:09.568Z",
  "color": "blue",
  "read": true
}
```

This is the **canonical harness-native aliveness signal** — no agent body is required to produce it, and its schema is stable:

```json
{
  "type": "idle_notification",
  "from": "<teammate-name>",
  "timestamp": "<iso-8601>",
  "idleReason": "available"
}
```

`idleReason: "available"` is the observed value. Other values almost certainly exist — `"terminated"`, `"blocked"`, possibly `"working"` — to be characterised as we see them during recon. The Go tool should parse `text` as JSON opportunistically: if `text` starts with `{` and parses cleanly, extract `type` and `idleReason` as structured fields; otherwise treat `text` as plain prose.

**The implications for the Go tool's aliveness diagnosis** are significant:

- The Go tool does NOT need to infer aliveness from mtimes. It can directly read the lead's inbox and count the most recent `idle_notification` per teammate.
- `idleReason: "available"` = teammate is alive and ready for input.
- Absence of any idle_notification from a teammate for a long time (despite tasks/messages that should have triggered one) = teammate is possibly stuck (formal `LIKELY_STALL` signal to be characterised in Scenario 5).
- If we observe `idleReason: "terminated"`, that's a clean teammate-exit signal.

**Finding 4: `read: true` flips immediately for active-session recipients.** All three messages in team-lead's inbox show `read: true`, despite the user taking no explicit action to "read" them. The lead IS the user's active foreground session, and messages arrive as conversation turns (and thus are flagged read) in the same event that wrote them to the inbox file. Observing an unread message will require sending to a teammate who is not actively running at the moment of send — to be tested in Scenario 5.

**No change to tasks dir.** Still `.lock` only; no `.highwatermark`. Spawning a teammate does not touch the task subsystem.

**S2b: after spawning `recon-beta` (second recon-cooperative teammate).**

Deltas from S2a:

1. `config.json.members[]` grew to 3 entries (team-lead, recon-alpha, recon-beta). `recon-beta` has `color: "green"`, same full non-lead schema as alpha.
2. `inboxes/team-lead.json` grew from 3 to 6 messages — same 3-message pattern from beta as from alpha (prose-ack → prose-idle → harness-JSON idle_notification).
3. No new files — no `inboxes/recon-alpha.json`, no `inboxes/recon-beta.json`, no changes in `tasks/`.

**Finding 5: Members are append-only in `config.json`.** Spawning does not reorder, remove, or restructure existing member entries. The array is the authoritative chronological record of team membership. A member that leaves the team (e.g. via shutdown request) presumably gets removed or flagged — to be characterised later if needed.

**Finding 6: Colors are harness-assigned sequentially.** Observed palette to date: `blue` (1st spawn), `green` (2nd spawn). Full palette TBD — the Go tool should treat the field as an opaque string and render whatever it finds, not assume a fixed palette.

**Finding 7: The spawn-to-idle pattern is consistent.** Each spawned recon-cooperative teammate produced exactly three inbox entries to the lead, in order: prose-ack → prose-idle → harness-JSON idle_notification. This is valuable for the Go tool: *"most recent `idle_notification` from teammate X"* is a reliable aliveness signal, and the ack+idle prose messages are per-agent-body noise that the tool can filter out (e.g. only structured JSON messages count toward aliveness computation).

**Finding 8: Recipient-lazy inbox creation re-confirmed at scale.** With two teammates both alive, only the lead's inbox file exists. Inbox files for `recon-alpha` and `recon-beta` will only appear if another teammate `SendMessage`s them — demonstrated in S4.

### Scenario 3 — Task lifecycle — COMPLETE

Single task created (ID "1") with owner assigned via separate `TaskUpdate`. Observed transitions: pending → in_progress → completed. The in-progress state was observed only via system-reminder snapshot; recon-alpha was too fast for a filesystem harvest between the two `TaskUpdate` calls.

**Finding 9: `TaskCreate` does NOT accept `owner`.** Owner is assigned via a separate `TaskUpdate` call. The accepted `TaskCreate` schema per the Claude Code main-session agent: `subject`, `description`, `activeForm`, `metadata`. **`owner` is not in this list.** Assigning an owner requires: (1) `TaskCreate` with the work fields, (2) `TaskUpdate(id, owner: "<name>")` separately.

**Finding 10: Task schema at creation, unowned, pending:**
```json
{
  "id": "1",
  "subject": "recon-s3-task",
  "description": "Recon scenario 3: update status from pending to in_progress then completed.",
  "status": "pending",
  "blocks": [],
  "blockedBy": []
}
```

Fields present: `id` (string-encoded integer), `subject`, `description`, `status`, `blocks[]`, `blockedBy[]`.

Fields notably absent: `owner`, `createdAt`, `updatedAt`, `activeForm`, `metadata`. The latter two may be omitted when not supplied by the caller; the timestamps are simply not recorded in-file (Go tool must use filesystem mtimes for recency).

**Finding 11: Task schema after `TaskUpdate(id, owner, status: in_progress)` (observed via forwarded system reminder):**
```json
{
  "id": "1",
  "subject": "recon-s3-task",
  "description": "...",
  "owner": "recon-alpha",
  "status": "in_progress",
  "blocks": [],
  "blockedBy": []
}
```

`owner` appears as a new field; `status` is updated in place. The existing fields are unchanged. No history log — the transition from `pending` to `in_progress` leaves no trace in the file itself.

**Finding 12: `TaskUpdate` that sets `owner` triggers a `task_assignment` inbox message to the new owner.** It also lazily creates the owner's inbox file. Message shape:

```json
{
  "from": "team-lead",
  "text": "{\"type\":\"task_assignment\",\"taskId\":\"1\",\"subject\":\"recon-s3-task\",\"description\":\"...\",\"assignedBy\":\"team-lead\",\"timestamp\":\"2026-04-21T11:20:28.564Z\"}",
  "timestamp": "2026-04-21T11:20:28.564Z",
  "read": true
}
```

Structured within `text`:
```json
{
  "type": "task_assignment",
  "taskId": "1",
  "subject": "...",
  "description": "...",
  "assignedBy": "team-lead",
  "timestamp": "..."
}
```

No `color` field on the outer message (sender has no color — sender is the lead). No `summary` field. Both appear to be absent for harness-generated messages.

**Finding 13: Completed tasks are DELETED from disk.** When `TaskUpdate` sets a task's status to `completed`, its `<id>.json` file is removed. After the full pending → in_progress → completed round, `1.json` no longer exists. Only active (pending / in_progress) tasks remain on disk. This is the most consequential finding in this scenario.

**Finding 14: `.highwatermark` is a monotonic total-tasks-ever counter.** After the first task was created (and then reaped), `~/.claude/tasks/<team>/.highwatermark` exists with contents `1`. The value equals the total number of tasks ever created for the team — *not* the count currently on disk. The Go tool's "completed task count" for a team is computable as `highwatermark - (count of JSON files in tasks/<team>/)`. The next-task ID is `highwatermark + 1` (strictly, this depends on whether reclaimed IDs are reused — unconfirmed, but the monotonic-id pattern is the simplest model and is consistent with observations).

**Finding 15: Task-assignment messages do NOT trigger an "acknowledged" prose reply** from recon-cooperative agents, despite the agent body instructing ack on every inbox message. Observed behaviour: recon-alpha received the `task_assignment`, immediately ran through steps 2–3 of its body (TaskUpdate in_progress → completed, send idle notification) without producing an "acknowledged" reply. The most likely explanation is that Haiku correctly interpreted the structured-type message as a task-work signal rather than a prose message, and deterministically routed to the task path. Alternative: the harness may suppress ack on structured-type messages. Either way, the behaviour is stable across our observation — the Go tool should treat absence-of-ack on `task_assignment` as normal, not as a stall signal.

**Finding 16: Subagents run asynchronously and are NOT stopped by a main-session stop instruction.** recon-alpha picked up and fully completed the task in ~8 seconds after the lead's `TaskUpdate`, despite the main-session (user's foreground Claude Code) being instructed to stop immediately after `TaskUpdate` returned. The teammates run as their own processes/contexts, driven by inbox events. Consequence: to observe a transient state, the teammate itself must be instructed to pause — not the main session.

**Summary of filesystem delta for one complete task round:**

- `tasks/<team>/<new-id>.json` created at `TaskCreate`, then deleted at `status: completed`.
- `tasks/<team>/.highwatermark` created (or incremented) when the first task in a lifecycle is created. Persists across task lifecycles.
- `teams/<team>/inboxes/<owner>.json` created lazily when the first `task_assignment` reaches them.
- `teams/<team>/inboxes/team-lead.json` grows with the teammate's idle notifications after task completion.
- `teams/<team>/config.json` — unchanged. Tasks do NOT touch team config.

### Scenario 4 — Message delivery and read semantics — COMPLETE

recon-alpha sent `"test-4a please reply"` to recon-beta via `SendMessage`. By the time the filesystem was harvested, beta had already woken, read the message, replied, and the two agents had entered a brief 2-hop ack loop before stabilising.

**Finding 17 (the critical one for the Go tool): `read: false` faithfully persists when the recipient is genuinely not processing.** Earlier (Scenario 2) I hypothesised that active-session recipients flip `read: true` immediately; in this scenario the converse case was observed directly.

After the user told the main-session (team-lead) to stop processing following `TaskUpdate`, recon-beta's prose idle notifications arrived at team-lead's inbox and landed with `read: false`:

```json
{
  "from": "recon-beta",
  "text": "idle: recon-beta has nothing pending",
  "timestamp": "2026-04-21T11:24:00.936Z",
  "color": "green",
  "read": false
}
```

**Interpretation:**
- `read: true` is set when the recipient processes the message as part of a conversation turn (actively reading their inbox).
- `read: false` remains set otherwise.
- A message arriving while the recipient is genuinely idle-not-polling stays `read: false` until their next turn.

**This is the canonical signal the Go tool uses for "unread count"** — no inference needed, just count `read: false` entries per-inbox.

**Finding 18: Peer-to-peer `SendMessage` lazily creates the recipient's inbox file.** `recon-beta.json` did not exist before alpha's send to beta. It was created the moment alpha's `SendMessage` tool call resolved. This extends Finding 1: every inbox file is recipient-lazy (created on first inbound), regardless of whether the sender is the lead (task_assignment from Scenario 3) or a peer (this scenario).

**Finding 19: Outbound prose messages include `summary`.** The message alpha sent to beta has:

```json
{
  "from": "recon-alpha",
  "text": "test-4a please reply",
  "summary": "Test message",
  "timestamp": "...",
  "color": "blue",
  "read": true
}
```

The `summary` was not present in my recon-cooperative agent body's instructions, and the agent wasn't explicitly told to provide one. Possibilities: the harness auto-generates a summary from `text`, or the `SendMessage` tool schema accepts an optional `summary` argument that Haiku inferred and provided. Either way, the Go tool should treat `summary` as **optional** — present sometimes, absent others. Harness-generated structured messages (task_assignment, idle_notification) do NOT include `summary`.

**Finding 20: Directive messages from lead to teammate post-spawn use regular `SendMessage`.** After spawning, the way the user (through the main-session = team-lead) instructed recon-alpha to send a message to recon-beta was by sending a regular prose message to alpha's inbox. Example from alpha's inbox:

```json
{
  "from": "team-lead",
  "text": "Recon task for you: invoke the SendMessage tool with `to: \"recon-beta\"` and `message` set to exactly the string `test-4a please reply` (no quotes in the body, no other text). You MUST use the SendMessage tool — writing the message as conversation prose is not sending and won't count. Once SendMessage returns, reply to me with a brief confirmation that it returned, then go idle. Do not wait for recon-beta to respond.",
  "summary": "Please DM recon-beta via SendMessage",
  "timestamp": "2026-04-21T11:23:43.560Z",
  "read": true
}
```

Clear separation:
- **Spawn-time instructions** → `config.json.members[].prompt` (not inbox, not replayable).
- **Runtime instructions** → regular inbox messages (replayable, inspectable, searchable).

**Finding 21: Cooperative-ack loops are observable but self-terminating.** Because my recon-cooperative agent body instructed "reply `acknowledged: ...` to every unread message", the exchange produced a 2-hop loop: alpha→beta "test-4a please reply", beta→alpha "acknowledged: test-4a please reply", alpha→beta "acknowledged: acknowledged test-4a please reply". The chain stopped after the third hop. Likely explanations: Haiku's pattern-detection avoiding further loops, or an implicit rate-limit. Worth noting for tool diagnostics: runaway ack-loops would be detectable as an oscillating sequence of messages between two teammates with rising "acknowledged:" nesting. Unlikely in real ATDD traffic but possible with naive bots.

**Filesystem deltas observed for this scenario:**

- `teams/<team>/inboxes/recon-beta.json` created (alpha's first send to beta).
- `teams/<team>/inboxes/recon-alpha.json` grew (team-lead's directive + beta's reply landed here).
- `teams/<team>/inboxes/team-lead.json` grew with beta's subsequent idle notifications — some `read: false` because team-lead session was idle-not-processing.
- `tasks/<team>/` — unchanged.
- `config.json` — unchanged.

### Scenario 5 — Silent recipient (LIKELY_STALL fingerprint) — IN PROGRESS

**S5a: spawn `recon-gamma` with subagent_type `recon-silent`.**

**Finding 22: Bulk-read-on-session-resume.** When I checked team-lead's inbox in this harvest, every message (21 total) was `read: true` — *including* the two beta-idle messages that were `read: false` in my Scenario 4 harvest. Between Scenario 4 (when the main session was idle-stopped) and Scenario 5a (when the main session resumed to spawn recon-gamma), the main session's wake-up processing flipped all outstanding unread messages to `read: true` in bulk.

Implications:
- `read: false` on a teammate's inbox is a **snapshot-in-time** signal, not a durable accumulating one.
- When the recipient is genuinely idle-not-polling, unread persists.
- When the recipient resumes activity, unread gets swept to read in bulk.
- For stall detection on the **lead's** inbox, `read: false` is unreliable because the user can wake the main session trivially.
- For stall detection on a **teammate's** inbox, `read: false` is highly reliable — a teammate that's genuinely stuck doesn't wake to sweep its inbox. This is the key signal for `LIKELY_STALL` and is precisely what Scenario 5 is built to characterise.

**Finding 23: `recon-silent` produced only the harness-injected structured `idle_notification`** — no prose "acknowledged", no prose "idle" message. Confirms:

- The harness-generated `idle_notification` (`{"type":"idle_notification","from":"<name>","timestamp":"...","idleReason":"available"}`) is truly auto-generated by Claude Code, independent of any agent-body behaviour. Even an agent that never invokes `SendMessage` produces one.
- This is the **canonical harness-native "alive and available" signal**. The Go tool should use it as the authoritative aliveness indicator per teammate — it cannot be absent just because the agent body is minimal or silent.

**Finding 24: Color palette order observed.** alpha = blue, beta = green, gamma = yellow. Three distinct, sequential. Palette position continues TBD (would need more spawns), but the order-by-join-time pattern is clear enough for the Go tool to treat `color` as an opaque string without needing to know the full palette.

**recon-gamma's inbox does NOT exist.** As expected — nobody has sent to gamma yet. S5b will change that and produce the core LIKELY_STALL fingerprint.

**S5b (T+0): after recon-alpha sends `"test-5 please reply"` to recon-gamma.**

recon-gamma's inbox was created:

```json
[
  {
    "from": "recon-alpha",
    "text": "test-5 please reply",
    "summary": "Test message",
    "timestamp": "2026-04-21T12:14:00.380Z",
    "color": "blue",
    "read": true
  }
]
```

**Note `read: true`.** This is the pivotal finding of the scenario.

**Finding 25 (reshapes the whole `LIKELY_STALL` model): Silent recipients produce `read: true`, not `read: false`.** When a message arrives for recon-gamma, the harness wakes gamma for a turn. Gamma reads the inbox (even silently), and the act of reading flips `read: true`. Then gamma processes the turn per its agent body (in this case, emit nothing), and the harness auto-emits a fresh `idle_notification` to team-lead. So a silent-but-alive teammate looks almost identical to a cooperative teammate on disk, differing only in:

- No outgoing `SendMessage` from gamma.
- Any expected reply does not appear in the sender's (alpha's) inbox.

The original mental model — *"stalled teammate = inbox has `read: false` messages"* — is WRONG. Silent teammates mark messages read the same as cooperative ones.

**The actual LIKELY_STALL fingerprint** is a **cross-inbox correlation**:

1. X received a message from Y at time T_receive (visible in X's inbox, `read: true`).
2. X has produced at least one harness `idle_notification` at time T_idle > T_receive (confirming X is alive).
3. No outgoing message from X to Y exists with timestamp > T_receive (visible by scanning Y's inbox for messages with `from: X`).
4. Elapsed time since T_receive exceeds some threshold (e.g. 10 minutes).

If all four conditions hold, X is in a LIKELY_STALL state: alive, aware of the incoming message, but not producing a reply. **This is exactly the April 2026 eval failure mode** — the Developer teammate emitted prose saying it was replying but never invoked the `SendMessage` tool.

The Go tool will need to:
- Enumerate all inboxes in the team.
- For each (sender, recipient) pair, find the most recent message X→Y and the most recent message Y→X.
- Compute the most recent `idle_notification` per teammate.
- Flag any pair where the relationship above holds.

This is O(N × M) work where N = teammates, M = average messages per inbox. Still trivial.

**Finding 26: `idle_notification` can carry a `summary` of the agent's last turn.** recon-alpha's `idle_notification` right after the send shows:

```json
{
  "type": "idle_notification",
  "from": "recon-alpha",
  "timestamp": "2026-04-21T12:14:06.833Z",
  "idleReason": "available",
  "summary": "[to recon-gamma] Test message"
}
```

The extra `summary` field describes what the agent did in the turn immediately before idling. Not present on fresh-spawn idle_notifications (first idle after spawn when nothing happened). Present when meaningful activity occurred. This is a **gift for the Go tool's diagnostic UX** — it can report *"alpha's last turn: '[to recon-gamma] Test message'"* without needing to parse the full conversation.

**S5b (T+60s): stall state is stable.**

- gamma's inbox: unchanged (one message, `read: true`).
- alpha's inbox: no new message from gamma.
- team-lead's inbox: unchanged since the immediate-post-send idle notifications.
- No new files, no mtimes changing.

**Finding 27: A stalled teammate emits exactly ONE idle_notification after receiving the message it fails to reply to, then stays silent.** This is the natural consequence of the harness wake-up model: gamma was woken to process the incoming message, did its (silent) turn, produced a post-turn idle_notification, and then had nothing to wake for. It does not emit "I'm still alive" heartbeats. The Go tool cannot use absence of *recent* idle_notifications alone to detect stall — a stalled teammate's last idle may be very old, but so may a healthy-idle teammate's.

**Finding 28: mtimes on inbox files give cheap recency without JSON parse.** `ls -la` on the inboxes directory shows when each was last modified. Useful for a fast first-pass diagnostic — the Go tool can narrow expensive parses to only-recently-changed inboxes when polling.

**S5b (T+5min): signature is durable.**

All state byte-identical to T+60s. File sizes unchanged. mtimes unchanged. No teammate woke. No new messages in any inbox. The stall state is completely stable — a stuck team genuinely stays stuck, no drift over time.

**Finding 29: Stall state is durable and idempotent.** The Go tool polling every N seconds (or even every N minutes) against a stalled team will return the same diagnosis every time, and the filesystem will look the same. This is important operational news for the tool: it can be safely invoked repeatedly without side effects on the observed state. False stalls are not a concern — the correlation will just keep reporting the stall.

### Scenario 5 summary — the LIKELY_STALL fingerprint

A teammate X is in the LIKELY_STALL state relative to sender Y when ALL of the following hold, simultaneously:

1. X's inbox contains at least one message with `from: Y`, `read: true`, `timestamp: T_receive` (X has received and read).
2. X has emitted at least one harness `idle_notification` with `timestamp > T_receive` (X is alive and completed a turn after receiving).
3. Y's inbox does NOT contain any message with `from: X`, `timestamp > T_receive` (X produced no reply).
4. `now - T_receive > stall_threshold` (e.g. 10 minutes).

Note the subtle distinction from the naive "unread = stalled" mental model:

- A *genuinely idle-not-waking* teammate leaves `read: false` on their own inbox (they haven't woken to process). This is **not** a stall; it's a not-yet-woken state. Usually short.
- A *stalled* teammate has `read: true` on the message in question — they *did* wake and *did* process — but produced no reply. The stall is visible only by cross-referencing the sender's inbox for the absence of a return message.

The Go tool must implement the cross-inbox correlation; a single-inbox read is insufficient.

### Scenario 6 — Teardown — COMPLETE

Graceful teardown characterised in two phases: a single cooperative teammate shutdown (S6a), and a full attempted-shutdown that hit the stall-blocks-shutdown failure mode (S6b).

**Finding 30: `TeamDelete` refuses while active members exist.** Error response:

```json
{
  "success": false,
  "message": "Cannot cleanup team with N active member(s): <names...>. Use requestShutdown to gracefully terminate teammates first.",
  "team_name": "<team>"
}
```

The harness enforces ordered teardown: shut down teammates first, then call `TeamDelete`. The error message is diagnostic-grade — it names the blocking teammates.

**Finding 31: Shutdown REMOVES the teammate from `config.json.members[]`.** This is not a "mark as terminated" flag — the entry is literally removed. Before S6a, members had 4 entries (team-lead, alpha, beta, gamma). After S6a, 3 (team-lead, beta, gamma). After S6b (partial — gamma couldn't shut down), 2 (team-lead, gamma). **Presence in `members[]` is the authoritative "currently-active" signal for the Go tool.**

**Finding 32: Shutdown PRESERVES the teammate's inbox file.** `recon-alpha.json` and `recon-beta.json` still exist on disk after their shutdowns. The historical record is retained — the Go tool can still inspect a departed teammate's inbox for post-hoc forensics.

**Finding 33: `shutdown_request` / `shutdown_approved` schema.**

Request (in teammate's inbox):
```json
{
  "type": "shutdown_request",
  "requestId": "shutdown-<epoch-ms>@<recipient>",
  "from": "team-lead",
  "reason": "<free-form text>",
  "timestamp": "<iso-8601>"
}
```

Approval (in lead's inbox):
```json
{
  "type": "shutdown_approved",
  "requestId": "shutdown-<epoch-ms>@<recipient>",
  "from": "<teammate>",
  "timestamp": "<iso-8601>",
  "paneId": "in-process",
  "backendType": "in-process"
}
```

Matching `requestId` between request and approval lets the Go tool verify each shutdown round-trip. If a `shutdown_request` was sent but no corresponding `shutdown_approved` has arrived after a threshold, the teammate is stuck-on-shutdown — the `UNTERMINABLE_STALL` state described below.

**Finding 34: No terminated-idleReason.** Terminated teammates do NOT produce a final `idle_notification` with `idleReason: "terminated"` (my earlier speculation was wrong). The termination signal is the `shutdown_approved` event, nothing else. `idleReason: "available"` appears to be the only value observed across all idle_notifications in the recon.

**Finding 35 (OPERATIONAL): Silent-stall teammates CANNOT be gracefully terminated.** `recon-gamma` received the shutdown_request (inbox shows `read: true`), woke (emitted a fresh idle_notification at 12:26:40), but produced no `shutdown_approved` — because approval requires `SendMessage`, which gamma's agent body never invokes. Consequence: the graceful teardown mechanism depends on the same tool-call that the stall has broken. **A teammate stalled on failure-to-invoke-SendMessage cannot be removed from the team by the harness alone.** This is a direct parallel to the April 2026 eval failure (Developer wrote reply as prose, never invoked SendMessage, couldn't be gracefully unstuck).

Options available to the TeamLead when encountering an unterminable stall:
1. **Kill the Claude Code main session** → team becomes a **zombie** (state not yet characterised).
2. **Manual force-cleanup**: `rm -rf ~/.claude/teams/<name>/` and `~/.claude/tasks/<name>/`. This is already documented in the team-lead-playbook under zombie-recovery.
3. **Escalate to the human via `AskUserQuestion`** — the Go tool surfaces the stuck state; the human decides whether to manually clean up.

The Go tool's diagnosis vocabulary gains a new state:

- **`UNTERMINABLE_STALL`**: teammate X is `LIKELY_STALL` AND a `shutdown_request` has been sent to them for which no `shutdown_approved` has arrived after threshold. Recommendation: manual intervention required; the harness cannot clean this up.

**Terminal state dependencies that need validation later:**

- Cleanly-deleted team (successful `TeamDelete` after all shutdowns approved): expected to remove `~/.claude/teams/<name>/` and `~/.claude/tasks/<name>/` entirely — can be inferred without further recon. Absent directory = deleted.
- Zombie team (main session killed without `TeamDelete`): expected to leave config.json + inboxes on disk with lead's session_id pointing to a defunct session. Can be characterised by having the user kill their Claude Code session and re-harvesting. Optional for rev-1 of this spec.

### Summary fingerprints for the Go tool

For a given team directory, the Go tool diagnoses one of:

| State | How to detect |
|---|---|
| `MISSING` | `~/.claude/teams/<name>/` does not exist. |
| `HEALTHY` | Team active; all members in `members[]` have emitted a recent `idle_notification` or are actively turning. No pending `LIKELY_STALL`. |
| `SOFT_WAIT` | Team active; a teammate has no recent idle_notification AND has no pending received message waiting for reply. (Possibly long-running but not stuck.) |
| `LIKELY_STALL` | Cross-inbox correlation (see Scenario 5 summary): X received from Y with `read: true`, X has emitted idle since receipt, Y has received no reply from X since receipt, elapsed time > threshold. |
| `UNTERMINABLE_STALL` | `LIKELY_STALL` PLUS X has received a `shutdown_request` with no matching `shutdown_approved` after threshold. Only manual intervention remains. |
| `ZOMBIE_TEAM` | Team directory exists but the lead's session (`leadSessionId`) is no longer alive. (Concrete detection TBD — requires cross-checking `~/.claude/sessions/` or `~/.claude/projects/` for session liveness.) |
| `CLEANLY_DELETED` | `~/.claude/teams/<name>/` does not exist. Indistinguishable from `MISSING` — the Go tool does not need to differentiate unless it has prior knowledge the team existed. |

Rev-1 of the spec consumes findings from Scenarios 1–6, plus the zombie-state characterisation below.

### Zombie state characterisation (Scenario 6 epilogue)

After the main Claude Code session was killed (Ctrl-C on the terminal, not `/exit`), the team directory was left in the exact state it was in pre-kill.

**Finding 36: The team directory alone cannot distinguish alive-but-idle from zombie.** `config.json` unchanged, inboxes unchanged, mtimes unchanged. The zombie signal must come from outside `~/.claude/teams/<team>/`.

**Finding 37: Session jsonl mtime is the authoritative lead-liveness signal.**

Every Claude Code session writes its transcript to `~/.claude/projects/<project-hash>/<sessionId>.jsonl`. The file's mtime updates on every session write (message, tool call, response). Once the session dies, the mtime freezes.

Observed for our zombie:
- Lead's jsonl path: `~/.claude/projects/C--Users-andre-AICode-atdd-agents/1de49820-6b28-4a1e-b5bc-cd0ee95e16d3.jsonl`
- mtime at harvest: 2026-04-21 13:30:04 (≈ 28 minutes stale at time of inspection).
- By contrast, my live recon session's jsonl was updating moments ago.

**The Go tool's `ZOMBIE_TEAM` check:**
1. Read `config.json.leadSessionId`.
2. Compute the project-hash from `config.json.members[0].cwd` (format appears to be: kebab-case transform of the absolute path — `C:\Users\andre\AICode\atdd-agents` → `C--Users-andre-AICode-atdd-agents`). Further path-to-hash observation may be needed on non-Windows systems.
3. Stat `~/.claude/projects/<project-hash>/<leadSessionId>.jsonl`.
4. If mtime is older than a threshold (a few minutes is a safe default), flag `ZOMBIE_TEAM`.

**Finding 38: `~/.claude/sessions/<pid>.json` carries session metadata including the OS PID.** Each file contains:

```json
{
  "pid": 27400,
  "sessionId": "1de49820-6b28-4a1e-b5bc-cd0ee95e16d3",
  "cwd": "C:\\Users\\andre\\AICode\\atdd-agents",
  "startedAt": 1776755859236,
  "version": "2.1.116",
  "peerProtocol": 1,
  "kind": "interactive",
  "entrypoint": "cli"
}
```

The Go tool can correlate a team's `leadSessionId` with a file here, extract the PID, and check process liveness via Go's cross-platform `os.FindProcess(pid); p.Signal(syscall.Signal(0))`. This is a **secondary/confirmatory** check — jsonl mtime is cheaper and usually sufficient.

**Note:** the session pid-json file is NOT cleaned up on crash — our zombie session 27400's file still existed at harvest. So presence of the pid-json is not proof of liveness; the Go tool should not rely on its existence.

**Finding 39: Subagents have per-session transcripts in a `subagents/` subdirectory.**

Layout:
```
~/.claude/projects/<project-hash>/<sessionId>/subagents/agent-<hex>.jsonl
```

Observations for our 3-teammate recon session: **26 agent-*.jsonl files**. Each file appears to be a single subagent **turn**, not a persistent per-teammate session — each wake seems to create a new file. First-line content is typically the full prompt the subagent received for that turn, with metadata including `agentId`, `promptId`, `summary` (e.g. `"Spawn recon-alpha teammate"`, `"Dispatch recon task to alpha"`).

For rev-1 of the Go tool this is out of scope (state inspection, not replay). For rev-2 (a "why did this agent stall?" forensic mode), these jsonls are the source of truth: they contain the raw conversation showing whether a given tool invocation actually happened or was just hallucinated in prose.

### Final state taxonomy for rev-1 of the Go tool

Updated from the earlier summary with concrete detection recipes for every state:

| State | Detection |
|---|---|
| `MISSING` | `~/.claude/teams/<name>/` does not exist. |
| `HEALTHY` | Team dir exists; `config.json.leadSessionId`'s jsonl has recent mtime; every member in `members[]` has a recent (or post-receive) idle_notification; no `LIKELY_STALL` triples. |
| `SOFT_WAIT` | Team dir exists, lead alive; one or more teammates idle with no pending received message. Normal waiting state, not stuck. |
| `LIKELY_STALL` | Cross-inbox correlation: X received from Y with `read: true` at T_r; X has an idle_notification at T > T_r; Y has received no reply from X since T_r; elapsed > threshold. |
| `UNTERMINABLE_STALL` | `LIKELY_STALL` PLUS X has received a `shutdown_request` without a matching `shutdown_approved` after threshold. Manual intervention required. |
| `ZOMBIE_TEAM` | Team dir exists; lead's jsonl mtime is older than threshold. Optionally cross-confirm with a process-liveness check on the PID from `~/.claude/sessions/<pid>.json`. |
| `CLEANLY_DELETED` | `~/.claude/teams/<name>/` does not exist. Indistinguishable from `MISSING` without prior knowledge. |

With these seven fingerprints and the documented schemas for `config.json`, inbox messages, tasks, and the various structured message types (`idle_notification`, `task_assignment`, `shutdown_request`, `shutdown_approved`), the Go tool's rev-1 can be built against a concrete, empirically-validated spec. The six recon scenarios (plus this zombie epilogue) are the authoritative data source for the build.
